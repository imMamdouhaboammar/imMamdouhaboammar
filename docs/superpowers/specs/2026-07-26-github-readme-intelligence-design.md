# GitHub README Intelligence System Design

## Goal
Create a reusable README layer that explains why each project exists, publishes a compact daily activity summary, and exposes aggregate profile metrics without revealing private repository names or activity details.

## User-facing experience
Every selected repository receives one expandable `<details>` block near the top of `README.md`. The block includes the repository mark, the recurring real-world problem that triggered the project, the practical goal, the audience, search-friendly topic phrases, and a three-to-five point daily update.

The profile README receives a separate metrics block showing GitHub-recognized commit contributions, current activity streak, longest activity streak, and contributions in the current calendar year.

## Architecture
The public profile repository is the central control plane. It owns project metadata, tested rendering code, GitHub API clients, profile metrics aggregation, and a reusable GitHub Actions workflow. Each project repository only owns a small scheduled caller workflow and a marker-delimited README block.

## Data flow
1. A daily or manually dispatched caller workflow invokes the reusable workflow in the profile repository.
2. The reusable workflow checks out the caller repository and the central README system.
3. The updater reads the matching project configuration and public GitHub activity.
4. A deterministic summarizer always produces a valid three-to-five point update.
5. When `OPENAI_API_KEY` exists, the updater may replace the deterministic wording with a concise AI summary. API failure never blocks the update.
6. The updater replaces only content between managed markers and commits only when the README changed.

## Profile metrics
The profile workflow queries GitHub GraphQL contribution collections in bounded yearly windows. It aggregates commit, pull request, issue, and review contribution days across public and token-visible private work. Private repository names, titles, URLs, and per-repository counts are never written to the README or logs.

`PROFILE_METRICS_TOKEN` is required for private contribution visibility. The token must belong to Mamdouh Aboammar and have the minimum scopes needed to read the contribution graph and private repositories.

## Interaction model
GitHub strips JavaScript from README files. Interaction is therefore native HTML only: `<details>` and `<summary>` provide expand/collapse behavior, while links and badges remain clickable. All substantive copy remains plain HTML/Markdown so search engines and answer engines can read it.

## SEO and AEO rules
- Lead with the problem and user intent, not tool jargon.
- Use one explicit answer to “What is this project?” and “Why was it built?”.
- Include natural topic phrases without keyword stuffing.
- Keep project claims bounded by current repository documentation.
- Preserve readable text outside images and SVGs.

## Security and privacy
- Workflows request `contents: write`, `issues: read`, and `pull-requests: read` only where required.
- No workflow runs on untrusted pull-request code.
- Secrets are optional except `PROFILE_METRICS_TOKEN` for private profile metrics.
- AI prompts contain public repository activity only.
- Bot commits generated by the updater use `github-actions[bot]`, not the user identity.
- Logs never print tokens, GraphQL responses containing private repository names, or raw private activity.

## Error handling
Missing project configuration, malformed markers, or an unreadable README fails before writing. Missing activity produces an honest “no public changes in the selected window” message. OpenAI errors are warnings followed by deterministic output. A no-diff run exits successfully without a commit.

## Testing
Node’s built-in test runner covers marker replacement, HTML escaping, deterministic summaries, project-card rendering, yearly metric aggregation, and streak calculation. CI validates every project configuration and verifies that generated blocks remain between three and five bullets.

## Rollout
The profile repository lands first. Ten project repositories then receive caller workflows and initial managed blocks on dedicated branches. Each repository gets a reviewable pull request; no default branch is modified directly.
